# Agent Runtime 当前实现与边界

## 当前执行路径

旧聊天请求由 `/api/ai/agent/sessions/:id/messages` 接收。会话所有者校验、管理员路由权限、语义任务解析、受限工具规划、工具白名单校验、证据合成和消息/运行记录由旧 Agent 控制器与引擎完成。所有模型工具计划进入 `agentExecuteTool`；未注册的名称在服务端被拒绝，Prompt 不能扩展注册能力。

第一阶段经营监测在 `agentnative.MonitorService` 中运行：规则扫描建立持久信号和任务，Worker 以租约认领，草案由数据库唯一约束保持幂等。普通聊天回合已在保存会话消息的事务中建立相同 `AgentWorkTask` 实体，任务 ID 同时返回聊天 UI，并可在工作台查看。监测任务通过 `signal_id` 关联信号；聊天任务没有信号，保存结构化目标/结果和发起主体。旧 Agent 待确认动作也会让关联任务进入 `WAITING_APPROVAL`，确认后完成任务并记录活动。

## 本轮融合状态

聊天工具注册表和 AgentNative Monitor 仍然是两条执行路径。聊天已创建持久任务并可跳转工作台，但当前任务表示同步聊天回合的结果，不表示 LLM 每一步的实时进度；还没有通用步骤记录、后台执行/恢复或共享工具执行入口。当前是持久任务联动，不是完整统一 Runtime。

## 后续统一契约

建议下一步在服务层定义 `ToolSpec` 和执行器接口，包含名称、描述、参数/结果结构、权限、风险、超时、副作用、幂等键和审计策略；聊天规划器与后台任务 Worker 只依赖该执行器。工具实现应调用共享业务服务，不依赖 Gin Context 或直接复用 HTTP Controller。

统一任务记录至少需要发起人、执行主体、任务类型、输入摘要、结构化结果、步骤、状态、幂等键、重试计数、租约和审批状态。不得保存 Provider 密钥或无必要的完整 Prompt。加入这些字段前必须核对现有部署的 MySQL 版本和线上迁移策略。

高风险写操作须独立授权和人工审批。现有旧 Agent 的支出/订单草稿确认语义与内部补货草案不同，不应合并成一个通用审批动作。
