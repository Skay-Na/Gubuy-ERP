## 1. 目标与边界

目标是把真实使用中的问题变成可复现的改进任务：Agent 自动记录运行过程与用户纠正，系统筛选和整理案例，Codex 定期分析、修改、验证并提交可审查的改进。评价重点是业务问题理解、计算口径、分析推理、预测质量和工具可靠性，而非仅提高答复速度。

“学习”分为三类，采用不同的生效规则：

| 类型 | 内容 | 生效方式 |
| --- | --- | --- |
| 用户记忆 | 本人的偏好、长期背景 | 继续使用已有 `ai_agent_memories`，本人可查看、修改、删除 |
| 案例学习 | 问题、失败原因、经核实的期望行为 | 进入评估集；Codex 据此修复工具、提示词或代码，验证后发布 |
| 预测校准 | 历史预测与之后实际值的偏差 | 按冻结的历史数据做回测；经评估后更新预测方法或参数 |

用户纠正、模型自评和“点赞/点踩”都是线索，不自动成为业务事实。生产 Agent 不直接修改代码、数据库口径、系统提示词或部署版本。Codex 可以自动完成分析、复现、修复和测试；影响业务结果的改动以可审查变更交付。

## 2. 当前基础与差距

- `ai_agent_messages` 已保存用户/助手消息，以及助手的 `status`、`task`、`evidence`、`trace`。`ai_agent_trace.go` 记录模型调用耗时与 token、工具计划和状态、停止原因。trace 当前是 `mediumtext` JSON，普通会话接口不返回。
- 对话按 `ai_agent_sessions.owner` 隔离；trace 读取接口校验所属用户。长期记忆已有明确保存、自动归纳和删除语义，不能拿来存业务错误案例。
- `erpctl agent eval --cases` 支持单轮、多轮、文本断言与任务结构断言；`docs/erpctl-cases.example.json` 增加了追问纠正样例。现有 `docs/agent-live-evaluation.json` 是一次运行结果，不是长期、冻结的金标准数据集。
- Agent 消息已有稳定 `run_id`，运行表记录模型、提示词/工具版本、耗时、token、工具/证据数量和失败码；反馈和候选案例 API 已接入。仍缺保留期清理、运行时采集故障指标和真实服务上的固定数据基线。

## 3. 总体数据流

```text
用户提问 → Agent 运行 → 结构化运行记录 ────────┐
                           用户反馈/后续纠正 ────┼→ 候选案例 → 脱敏与核实 → 评估集
                           预测到期后的实际值 ────┘                           │
                                                                            ↓
                                                   Codex 周期任务 → 修复 → 回归/回测
                                                                       ↓
                                                         变更报告 → 审查 → 发布
                                                                       ↓
                                                         监测新版本与回滚
```

运行采集在 ERP 后端完成，不依赖 Codex 在线。周期任务只读取受控的案例导出和测试环境，不能用生产数据库做写入测试。

## 4. 阶段和交付

### 阶段 0：基线与数据约定

**目的：** 先知道当前 Agent 的真实表现，并固定以后可比较的口径。

- 整理代表性的销售、库存、财务、工资、国补、多轮追问、无数据、草稿和预测问题。建立最小金标准集；每例标明主题、指标、时间范围、应使用的证据、允许的澄清、禁止的结论。
- 用隔离测试库生成固定夹具；给每个样本记录 `dataset_version`、参考时间 `as_of`、业务口径版本和模型/提示词/代码版本。相对时间问题必须冻结参考时间。
- 在相同环境运行现有 `erpctl agent eval`，保存每例结果、耗时、token、调用次数及失败分类，形成 `baseline` 报告。先检查现有评估命令是否会产生草稿或业务副作用，并在专用测试账户/库运行。

**验收：** 一条命令可在固定测试环境重复运行基线；同一案例的期望与数据来源明确；报告区分“计算错误”“理解错误”“没有足够数据”。

### 阶段 1：结构化运行采集

**目的：** 每次真实运行都能定位和诊断，不依赖翻阅整段聊天。

- 给一次请求生成 `run_id`，关联用户消息、助手消息、session、trace、反馈和后续案例；记录模型、当前固定提示词版本、配置档位、总耗时、token、状态和失败码。
- 从已有 task/tool/evidence 中提取结构化字段：问题主题、操作、指标、数据集、时间范围、工具调用、错误码、结果行数、是否为空/截断、证据来源、草稿创建与确认状态。写入失败不得让正常对话失败；记录采集故障计数。
- 创建 `ai_agent_runs`（索引字段和版本）。原始 trace 仍保留在消息表中；新表保存查询和聚合所需字段，避免用 JSON 模糊搜索整张消息表。先提交正常消息，再尽力写运行行和失败候选；采集失败只记服务端日志，不改变已完成的答复。
- 不采集模型思维链、API key、密码、验证码或完整数据库结果。业务实体 ID、用户姓名、手机号等在导出时脱敏。设置可配置的原始记录保留期（初始建议 90 天）；聚合指标和已脱敏评估案例可保留更久。删除会话/用户数据时同步处理关联记录。

**验收：** 可凭 `run_id` 重建一次执行的模型调用、工具、证据与终态；普通用户只能看到自己的记录；运行日志写入失败不改变 Agent 答复。

### 阶段 2：反馈与候选案例发现

**目的：** 自动找出高价值问题，并让用户轻松指出错误。

- 在助手消息上增加“有帮助 / 有问题”，有问题时可选“理解错、数字或口径错、证据不足、预测不合理、速度/失败、其他”并写短说明。接口以所属 session 校验权限；同一用户对同一消息可更新反馈。
- 自动规则创建候选：请求失败或超时、工具错误、达到步骤上限、重复无效工具调用、查询截断后做全量结论、证据为空却给确定数字、草稿未确认却声称执行成功、用户紧接着纠正上轮主题/数字、预测到期偏差超阈值。
- 规则只给“疑似问题”及证据，不声称答案一定错误。对重复问题聚类并计数，按严重度 × 出现频率 × 业务影响排序。创建 `ai_agent_feedback` 与 `ai_agent_cases`；案例状态为 `new / triaged / labeled / fixed / rejected / monitored`，保留来源 run、发现规则、版本、核实结论。
- 管理工作台支持筛选、查看关联 trace 与证据、标注正确口径、排除误报、导出脱敏案例。初版可先做后端分页接口和 CLI 列表，UI 后补；不需要实时推送。

**验收：** 用户 2 次点击即可报错；失败运行自动进入候选；反馈和案例均不能越权读取；同一问题不会无限生成重复任务。

### 阶段 3：可重复评估与防回退门禁

**目的：** 让 Codex 的修改有客观判断标准。

- 扩展 `erpctl agent eval`：支持多轮对话、固定参考时间、夹具版本、期望 task/工具/证据、数值容差、拒答/澄清条件、草稿确认状态；输出机器可读 JSON 和人类可读摘要。
- 分为三组：冻结核心集（不随单次优化改变）、新增真实案例集、隐藏保留集。用户反馈须核实后才能升格为“期望答案”；涉及金额和业务口径的答案由数据库断言或明确公式给出，不能用另一模型生成的回答作唯一裁判。
- 同一数据快照下比较候选版本与基线：正确率、严重错误数、证据充分率、误报/漏报、耗时 P50/P95、token 成本。保留逐例差异，失败可复现到 run ID 和案例 ID。
- 发布门禁建议：核心集通过率不下降；关键财务/订单/工资口径 100% 通过；新增目标案例通过；无新的未授权写入或越权；成本与 P95 耗时没有明显恶化。阈值以阶段 0 基线定稿，避免凭空设定百分比。

**验收：** 在隔离库跑同一命令可复现结果；至少能检测“修好 A、弄坏 B”；评估失败能指到具体输入、数据快照和断言。

### 阶段 4：Agent 的受控运行时学习

**目的：** 不等发版也能吸收安全、明确的用户信息。

- 保持现有个人记忆机制，只允许用户资料、回答偏好、长期背景进入自动记忆；对已有条目继续提供来源和删除能力。
- 新增“待核实业务知识”库仅供管理：常见别名、页面/工具用法、已确认的指标解释等。它不能覆盖代码中的计算口径；每条需来源、适用范围、版本、审核状态和到期/复核时间。只检索 `approved` 条目，注入时标为参考资料而非最高优先级指令。
- 对用户纠正可在当前会话立即采用，但跨会话的共性修正先形成案例，再进入评估/代码更新或经审核的知识库。高风险领域（财务、工资、库存、订单写入）默认不自动提升知识。
- 每次知识条目生效记录其 ID，便于判断某条知识是否提高或损害回答质量；效果差可撤回。

**验收：** 新偏好跨会话生效；未经核实的用户说法不改变全体用户答案；删除记忆和撤回知识能停止后续使用。

### 阶段 5：Codex 周期优化任务

**目的：** 把案例定期变成经过测试的代码改进。

- 已有 `erpctl agent cases` 只读列出当前账号的候选案例，并对登记的人员姓名、手机号、工号、客户地址、订单号和邮箱做脱敏；仍需补齐按批次导出、游标和去重交接文件。
- 已配置本地每周一 09:00 的 Codex 对话任务；新出现严重口径错误可手动提前触发。任务先检查工作区状态，读取脱敏新案例与上轮报告，分流为数据问题、提示词问题、工具/算法缺陷、产品需求或误报。只有能在隔离环境复现时才改代码。
- 每批只解决可复现且收益最高的少量问题。Codex 更新评估案例、修复实现，运行 Go 测试、前端相关测试/构建、`erpctl agent eval` 和必要的预测回测。生成 `docs/agent-improvement-runs/<batch-id>.md`：案例、根因、改动、前后结果、失败项、成本变化、需人工判断的问题。
- 对可验证的修复提交可审查 diff 或 PR；不自动合并或部署。无法核实的案例记录阻碍与需要的数据，不凭猜测修改业务规则。周期任务在无新案例时保持安静；失败、完成可审查改动或需要判断时通知。由于它是本地任务，运行时需要 Codex 桌面应用和项目目录可用。
- 调度凭据只允许读取受控案例与测试环境，不能给 Codex 生产数据库写权限；敏感样本只在本机受限目录，报告只引用脱敏内容。任务要有运行锁、超时、失败重试上限和上一批次游标，避免重入和重复处理。

**验收：** 用一批已标注案例手动触发完整周期，能自动产出修复与前后评估报告；无可修复案例时不会产生无意义改动；任务中断后能按批次继续。

### 阶段 6：预测闭环与上线监控

**目的：** 验证 Agent 是否真的提高了分析和预测能力。

- 对每次预测记录预测对象、指标、粒度、目标时间窗、生成时点、训练数据截止时间、方法/参数版本、点预测和可选区间、样本量及不足提示。到期后用同一业务口径计算实际值，生成误差；禁止用目标时间之后的数据参与当时的预测。
- 用滚动起点回测比较当前方法与简单基线（如去年同期或近月均值）。按数据充足程度、门店/商品、预测跨度分组，观察 MAE/WAPE 或适用的误差指标；零值、极小分母单独处理。预测建议若有实际业务动作，也要记录是否被采纳和事后结果，不能把相关性当作收益。
- 发布后监测版本级错误率、反馈率、严重口径错误、预测误差、耗时和费用。出现关键指标退化时暂停自动知识注入或回滚 Agent 版本，并保留回滚前后报告。

**验收：** 能回答“上个月的三个月销售预测后来差了多少、相比旧方法是否更好”；每个预测的实际值可追溯到数据库口径和时间截点。

## 5. 接口、数据和代码落点

| 范围 | 建议落点 | 说明 |
| --- | --- | --- |
| 运行采集 | `erp-backend/controllers/ai_agent_controller.go`、`ai_agent_trace.go`、新 service | 保持 controller 只做请求编排，分类/导出逻辑移出 controller |
| 数据表 | `erp-backend/models/ai_agent.go` 或独立模型文件；`config/db.go` | 新增 runs、feedback、cases、prediction_snapshots；大表索引和保留清理需单独验证 |
| API | `erp-backend/routers/router.go` | `POST /ai/agent/messages/:id/feedback`；管理端分页查询/标注案例；权限均核对 owner 或专门管理角色 |
| 前端 | `src/components/AIChatAssistant.vue`、`src/composables/useAIAgent.js` | 消息反馈入口；案例工作台作为独立管理页面，不挤进聊天窗 |
| CLI/评估 | `erp-backend/cmd/erpctl/eval.go` 与新 case 命令 | 批量导出、固定数据集评估、JSON 报告、非零退出码 |
| 周期任务 | 本地 Codex 自动化配置 + `docs/agent-improvement-runs/` | 调度器只负责唤起；实际读写边界在 CLI、测试库和 Git 工作区中实施 |

建议表的关键字段：

- `ai_agent_runs`：`run_id`、`session_id`、`user_message_id`、`assistant_message_id`、`owner`、`status`、`topic`、`operation`、`model`、`prompt_version`、`tool_version`、`started_at`、`duration_ms`、`tokens`、`failure_code`。按时间、owner、status、topic 建索引。
- `ai_agent_feedback`：`assistant_message_id`、`owner`、`rating`、`category`、`comment`、`created_at`、`updated_at`；消息和 owner 唯一，允许改评。
- `ai_agent_cases`：`case_id`、`source_run_id`、`fingerprint`、`detector`、`severity`、`state`、`verified_label`、`dataset_version`、`assigned_batch_id`、时间戳。`fingerprint` 用于去重，但保留出现次数。
- `ai_agent_prediction_snapshots`：`run_id`、`metric`、`target_start/end`、`as_of`、`method_version`、`forecast_value`、`actual_value`、`evaluated_at`。实际值到期后填充，预测原值不可覆写。

表结构在实现时再根据 MySQL 实际版本、数据量和查询计划定稿；历史 `trace` 的回填应限速且可重复执行，避免启动时一次性扫描全库。

## 6. 实施顺序、工期与决策点

| 顺序 | 依赖 | 预估工作量 | 阶段结束可交付 |
| --- | --- | --- | --- |
| 0 基线 | 无 | 2–4 天 | 固定夹具、初始评估报告 |
| 1 运行采集 | 0 的字段约定 | 3–5 天 | 可查询的结构化 run |
| 2 反馈与案例 | 1 | 4–7 天 | 反馈入口、候选规则、案例列表/导出 |
| 3 评估门禁 | 0、2 | 5–8 天 | 多轮与数值断言、版本对比 |
| 4 运行时学习 | 2、3 | 3–5 天 | 经审核知识与效果追踪 |
| 5 Codex 周期任务 | 2、3 | 3–5 天 | 每周自动分析、修复、报告的可审查流程 |
| 6 预测闭环 | 1、3 | 4–7 天起，之后持续积累 | 预测快照、到期误差和回测 |

工期是开发估算，不含等待预测到期的自然时间。阶段 4 与阶段 5 可在阶段 3 完成后并行；阶段 6 的采集字段应在阶段 1 预留，避免早期预测样本丢失。

实施前需要确定的业务配置：原始日志保留期、谁能查看跨用户案例、周期任务运行的机器和频率、改动采用本地 diff 还是 PR。建议默认：90 天原始记录、仅系统管理员可看跨用户脱敏案例、每周一次本地任务、提交可审查 diff/PR 后人工发布。这些是默认建议，不作为已授权的生产配置。

## 7. 最小可用版本与最终完成标准

**首个可用版本：** 阶段 0–3。它已能持续发现真实问题、接收反馈、转成固定评估、验证后续修改；不会把“存了很多日志”误称为 Agent 学会了。

**完整闭环完成：** 阶段 0–6 全部通过验收；至少完成两次周期优化批次，其中一次修复真实问题，且新版本在冻结核心集、真实案例集和预测回测上有可比较结果；出现回退时能追溯并恢复上一版本。
