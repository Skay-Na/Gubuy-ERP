# ERP Agent 数据访问与分析审查

业务模块说明书注册方式见 [说明书注册](agent-manual-registration.md)。Agent 会先读取模块摘要，再按当前问题加载相关规则；说明书不能授予数据权限或代替实时查询。

## 全员提成规划修复

“查询员工上月提成”曾被正确识别为全体员工、上个自然月和应计提成，但任务的 `basis` 是中文“应计提成（commission_payable）”，统一报表只接受英文枚举，导致错误落到要求员工姓名的单人工具。现在统一中文/英文提成口径后直接复用员工月度报表；工具兜底也把无姓名的全员提成请求作为全员范围处理。应计提成与实际已付仍严格区分。

回归中还发现模型有时会把没有“实发/已发/实际支付”字样的“上月提成”猜成已发提成。现在只在用户原话明确表示实际付款时保留 paid；仅问提成或工资时恢复应计口径。

## 模糊问法与分析失败修复

隔离库真实模型测试新增“上个月卖得怎么样”“上个月收支情况怎么样”“未来三个月销售额大概多少”。模糊销售表达能归纳为销售额、订单数、件数和客单价；无收支流水时不再启动泛化规划器反复尝试数据集，而是基于成功的标准报表明确回答“没有找到符合口径的记录”，状态完整且不把缺记录当作零。收支报表还支持规范化“净收支”指标。

预测工具明确返回可预测性不足时，现在直接用用户可读的中文解释已有完整月份数和不足原因，停止无效重试，不再给出“AI无法生成结论”类兜底文案。对预测参数的明确指引把这条问法从多次无效计划降到一次工具调用。有效预测仍需按历史基线工具的数据要求，并会说明算法与样本限制。

## 国补未回款余额补齐

“国补还有多少没有回款”现在映射为 `subsidy_pending` 当前存量指标。Agent 与国补概览页面共用同一计算方法：有效国补订单累计应回款（新字段优先，旧订单回退国补金额）减去已登记国补结算回款，最低为零。没有指定月份时不强加本月筛选；历史月份余额仍需单独的时间截点算法，不能套用当前余额。隔离库测试覆盖新旧订单、取消订单和结算记录；真实模型用用户原话完成回答。

## 2026-10-05 实施结果

当前会话入口为 `/api/ai/agent/sessions/:id/messages`。本次将执行链改为：语义任务理解 → 业务报表或工具查询 → 完整性核对 → 自然语言回答。旧关键词意图重写、第一月份覆盖全部计划、原始工具结果直接拼入正文的流程已移除。

### 任务与连续对话

任务保存目标、主题、操作、指标、全部期间、对象、口径和假设。后续追问结合最近对话和上轮任务重新理解；当前纠正优先，换主题清除旧条件。模型遗漏明确月份时要求重新理解，不强行改写每个工具的日期。真正缺少必要信息才澄清。

### 数据与计算

业务目录覆盖账户、划拨、分类、商品、库存、员工、考勤、订单及明细、支出、财务流水、采购入库、待入库、盘点、库存流水、成本修复、国补回款和导入状态。敏感凭证、管理员密码、员工 PIN、原始图片与会话内容不进入业务目录。工具仅允许目录内字段与参数化筛选，无自由 SQL。

统一报表覆盖：有效订单折后销售额、订单数、件数、客单价与订单毛利；工资/提成应发汇总；已登记收支；当前库存概况。工资沿用员工管理月度报表算法，已付工资仍以财务发放记录为依据。销售期间使用订单日期，避免商品明细创建时间错位。库存可用件数不含样机，估值按平均成本并包含样机，低库存阈值明确为 3 件。

其他问题使用通用查询，支持明细、聚合、分组、趋势和历史基线预测。明细每次最多 30 行，需要规划分页；不是任意跨表 JOIN 或任意算法执行环境。新增业务表仍需要注册目录与业务口径。

### 可靠性与回答

- 核对所有期间及每个标准指标在每个期间的覆盖；日期区间可连续合并，缺口不能视为完整。
- 目录仅供模型内部使用；无效工具结果返回规划修正，不成为业务证据。
- 循环计划、查询预算耗尽、空输出或截断输出不能悄悄标记完成。
- 最终回答引用证据 ID；核对发现缺项后，最多追加两次补查，受总工具预算约束。
- 标准报表数字与变化率由程序计算和呈现；回答中的数值与报表证据核对。该校验不是完整的语义证明，模型仍可能误解指标关系。
- 无记录不冒充实际零；预测说明样本限制；没有销量和周转证据不能仅凭库存快照判断健康或补货合理。
- 正文展示结论和业务数字，查询依据默认折叠，原始详情再次折叠。未完成分析明确标识，并保留已核实报表。

### 思考等级与诊断

界面提供自动、快速查询、标准分析、深度分析。当前 DeepSeek 适配为 low/high/max，输出预算分别 8192/16384/32768，工具步骤上限 6/10/14。自动模式可根据语义任务调整。其他供应商不盲目发送不支持的推理参数。

服务端保存模型耗时、完成原因、token 用量、工具计划、执行状态和停止原因；不保存模型思维链，不向普通消息接口返回内部 trace。整体请求上限四分钟，前端超时略长于服务端。

## 验证与边界

- 隔离 MySQL 审计库运行 `go test ./controllers` 通过；覆盖双月份、口径纠正、全部员工、指定员工、应发/已付区别、目录不成为回答、空输出、截断、期间及指标缺失、最终核对后补查、状态持久化。
- `go vet ./controllers ./models ./config ./routers` 通过；前端 `npm run build` 通过，有既有大包警告。
- 使用实际 DeepSeek 模型和隔离库虚构数据验证连续四轮：8/9月销售对比 → 那9月呢 → 我说的是订单数量 → 现在库存怎么样，最终四项均通过。详见 `agent-live-evaluation.json`。这不是生产数据统计，也不代表所有问法或预测场景已通过真实模型测试。
- 同一隔离库真实模型回归扩展到 9 个日常问法，覆盖销售对比与追问、模糊销售、无匹配收支、库存、国补余额、全员提成和样本不足预测，最终 9/9 完整回答，无原始查询参数泄露。该隔离库中两个月销售样本、国补余额等数值是测试夹具，不代表实际经营数据。
- Playwright 使用模拟接口验证思考等级和折叠依据，避免写入生产数据。
- 预测目前仍是历史基线，并未训练专门的经营预测模型；未知指标的语义完整性部分依赖模型核对，不能保证所有复杂问题一次回答正确。
- 本次修改为工作区实现，尚未更新运行中的生产容器。全仓其他既有改动未随本次处理发布。
