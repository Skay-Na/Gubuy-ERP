## 1. 范围与使用方式

- 入口索引：[`src/router/index.js`](../../src/router/index.js)、[`erp-backend/routers/router.go`](../../erp-backend/routers/router.go)。

- 每次变更先查第 2–4 节，定位完整影响链；检查第 5 节是否涉及已知断点；按第 6 节选择验证。业务规则变化时在同一提交中更新本文，保留“现状/缺陷/待确认”的区别。

### 员工离职交接与结算（2026-10-23）

- 管理端从人员列表发起交接，管理员在每张交接单上手工登记最后工作日和当月假期天数；当前没有独立假期日历及维护人，假期天数是本次交接的输入快照。已批准带薪假没有自动折算为签到日的规则；离职底薪严格按 `底薪快照 ÷（离职月日历天数 − 假期天数）× 离职月截至最后工作日的签到天数` 计算，签到日取 `DailyAttendance.check_in` 非空的不同日期，按分四舍五入。
- 当前管理端接口注册在 `/api` 路径下并通过 `AdminAuthRequired` 中间件鉴权：交接单读写为 `/api/employees/:id/offboardings`，任务/结算为 `/api/employee-offboardings/:id/...`，看板提醒与复核为 `/api/employee-offboarding-alerts...`。前端请求和 `operationRoutes` 必须与这些实际路径一致。
- 离职开始时，事务锁定员工档案，状态改为 `offboarding` 并记录最后工作日；最后工作日之前仍可登录，超过该日拒绝 PIN 登录和已有员工 JWT 请求。订单创建及配送/安装人员指派也锁定员工状态；通过 `CreateOrder` 的员工端、管理员、AI 开单共用该校验。员工完成交接结算后状态变为 `departed`。
- 交接任务在同一事务内生成：库存/现金/资产/账号/客户清单及该员工开单、送货或安装的未结订单。离职交接中仍新建的员工订单也会在开单事务里追加未结订单任务。非自提且配送/安装未完成的订单生成高优先级待履约告警，取消时关闭该告警，配送/安装完成时自动关闭。
- 普通提成和商会分摊按订单 `created_at` 归属。离职结算从最后工作日所在月的订单开单时间计算至最后工作日，即使订单此后取消也保留开单时提成快照；后续取消、红冲、关联退款会另外产生高优先级告警，不静默改写已确认应付额。交接单仅在最后工作日结束且全部任务验收后确认结算，月报随后采用离职结算快照，避免把整月底薪重复列入；应付确认不等于实际支付，实付仍以财务流水为准。
- 取消/红冲、专业记账退款、普通支出退款、Agent 记账确认，以及配送/安装状态更新都检查告警副作用与事务回滚；新告警、交接任务和状态纳入 `operationRoutes`、快照撤销表与系统重置。看板提醒取全部日期的待处理离职订单告警，不随经营报表期间切换；告警复核仅记录说明，不直接改财务或薪资。
- 数据表 `employee_offboardings`、`employee_handover_tasks`、`employee_offboarding_alerts` 由 `AutoMigrate` 创建，SQL 全库备份会包含，恢复计数已纳入；新增结构尚未做隔离库导出/恢复演练，因此本次备份恢复仍未验证。管理员、员工终端、AI/图片导入共用订单写入路径；报表月报覆盖离职结算快照；员工清单导出包含任职状态与最后工作日，订单导出保留原始员工归属字段，不重写历史订单。
- 订单管理新增临时“已删除员工待跟进”快捷筛选：只匹配 `employee_id` 指向软删除员工档案的正常订单，排除空经办人订单；待跟进条件为仅付定金、国补状态 1/2，或非自提订单明细仍未完成配送/安装。列表和导出复用同一查询条件，不修改订单归属或状态。国补状态 2 仅表示已提交且未标记回款；因回款没有逐单核销，筛选结果是待核候选，不证明逐单实际欠款。
- 写入成功后应刷新当前展示的关联数据；各 composable 实例中的本地数据不代表全局已经刷新，需检查调用方和切页后的重载。
- 管理端订单详情的“编辑推荐信息与提成”更新订单推荐人/渠道文本与奖励金额；奖励已发放后两项都禁止修改。保存写入 `orders`，由已有 `/api/orders/:id/referral-fee` 操作历史捕获并可撤销；历史详情会显示推荐人/渠道的前后值。此字段也驱动员工端推荐单筛选和员工绩效过滤（名称含“老板”时排除个人绩效），不能只按展示备注理解。

## 3. 核心数值来源与边界

| 数值 | 当前来源/计算 | 禁止混淆的概念 |
|---|---|---|
| 可用自有库存 | `Product.store_stock + cloud_stock`，库存查询与开单校验使用此口径 | 样机、停用主仓、云端代发能力不是可售自有库存；系统不据此触发缺货或囤货提醒 |
| 成本重算总量 | `productTotalStock` 含主仓、门店、云仓、样机；最近成本基准 + 有效库存事件重放 | 与 AI 当前估值范围不同，主仓有旧余额时须核对 |
| 订单单位成本 | `orderCostSnapshot` 优先正 `avg_cost`，否则 `latest_cost`，创建时存 `OrderItem.unit_cost`；缺有效成本拒单 | 员工登记实物数量不凭空生成成本；零成本库存须经管理员核价后才可开单；当前商品成本不是历史订单成本 |
| 入库成本与资金 | 管理员入库和遗留申请批准都只增加库存、记录成本；创建新订单时读取成本快照并计入毛利 | 入库成本不是采购付款，不生成账户扣款；销售收款仍按订单实际支付账户入账 |
| 商品平均/最新成本 | `RecalculateSingleProductCosts` 根据最近审计基准和库存事件重算；调拨不改变总价值，作废采购不作为有效采购 | 不能简单平均全部历史进价；不能无视成本事件数量与当前数量不符 |
| 商品总额 | 非赠品成交单价 × 数量之和，赠品单价为 0 但仍有数量与成本 | 不等于客户应付或已收现金 |
| 折后销售额 | 看板/Agent 为有效订单 `total_amount - discount_amount` | 月报、排行、导出未完全统一，见 R6 |
| 国补优惠 | 当前代码为基数 × 15%，封顶 1500、两位小数；混付优先公户原始刷卡额作基数 | 这是当前程序规则，不是外部政策验证；换新组合前后端差异见 R7 |
| 客户应付 | `max(0, total_amount - subsidy_amount - trade_in_amount - discount_amount)` | `actual_pay_amount` 字段名虽含 actual，定金单时仍是应付全额 |
| 实收与尾款 | 创建定金单收定金，否则收客户应付；有效定金单待收为 `actual_pay_amount - deposit_amount` | 定金转全款当前是先退定金后收全额，不是直接收入差额 |
| 混付实收 | `payment_breakdown` 保存实际入账拆分；国补非定金混付公户原始额需减国补成为净到账 | 支付方式枚举不是账户 ID；历史回退路径需单独检查 |
| 国补累计未回 | 有效国补订单逐笔取正 `subsidy_pending_amount`，否则回退 `subsidy_amount`；减全部回款、最低为 0 | 非按所选期间计算的现金收入；资料状态不是逐单回款凭证 |
| 期间现金流 | `FinancialLog` 的收入/支出，汇总排除 `reversal_pair_id` 非空；划转/校准另列 | 不等于销售额、利润；原始审计列表可保留成对流水 |
| 看板订单毛利 | 折后销售额 − 订单明细成本快照 − 配送 − 安装 − 推荐奖励 − 员工提成 − 换新金额 | 含未收齐/未履约的有效订单；代码注释的 completed sales 不能作为已履约过滤证据 |
| 看板经营净利润 | 上述毛利 − `Expense` 中非 `采购货款`/`以旧换新` 的费用 | 采购付款不是再次确认销售成本；专业记账费用覆盖不全见 R4 |
| 看板零成本售出提醒 | 全量未取消、未软删除订单明细中 `unit_cost <= 0` 的明细条数，不受看板期间筛选影响 | 仅是待核数量；不代表商品当前成本就是历史成本，也不自动估算毛利；处理入口为系统设置中的逐笔历史成本修复 |
| 普通订单提成 | 非国补以应付额为基础，国补以商品总额为基础，按可计提商品销售额占比分配后乘员工比例，存订单快照 | 商品 `no_commission` 与明细快照、整单不计提成、老板客户规则需一起检查 |
| 商会提成 | 创建时可计提销售额 × 1% 形成池；历史零池有回退规则；按订单时点符合条件的员工分摊，分余数按 ID 分配 | 不能直接当作开单员工个人提成；当前与历史员工集合用途不同 |
| 应发工资 | `monthlyEmployeePayrollReport`：当前底薪 + 应计提成 − 请假扣款；默认每月免假 4 天；未登记月请假时回退缺勤天数 | 未找到月薪结算快照；事后改底薪可能影响历史重算，需明确业务要求 |
| 已登记工资/提成实付 | `FinancialLog` 支出按类别及日期查询，排除成对冲销 | 没有发放流水时只能说明未找到登记，不能推断确实未发 |

### 状态和历史字段

- 订单 `order_status`：1 正常、2 取消；支付 `payment_status`：1 定金、2 全款。统计需明确有效状态和软删除过滤，手写 `Table/JOIN` 不应假设 GORM 自动加软删除条件。
- 国补 `subsidy_status` 定义 0/1/2/3，但回款记录没有 `order_id`，不能仅凭累计回款将某单视为已回款。
- 发货方式新流程使用 1 门店自提、4 云仓发货，2/3 保留历史兼容。4 优先扣自有云仓，不足代发，保存实际 `cloud_deduction_qty`；取消按实际扣减退库，兼顾历史 `store_deduction_qty`。
- 仓库代码：1 历史主仓、2 门店、3 云仓、4 样机（库存流水/调拨）；多个新写入口把 1 归到 3，不代表可以删除旧字段或统一把所有历史主仓记录解释成云仓。
- 核心业务时间多使用服务端 `time.Local`；订单发生时间、付款时间、安装时间和工资归属月不是同一个维度，跨月退定金/退款及补录需检查日期边界与部署时区。

## 4. 典型影响链与一致性要求

以下是后续开发要求；并非宣称当前所有入口已满足。

1. **开单 → 库存/收款 → 后续履约**：订单与明细、实际库存扣减、库存/财务流水、账户余额及一次性导入/草稿消费应同成同败；并发购买不能超扣自有库存。取消须同时考虑实际扣库、实收拆分及已经发生的其他费用。
2. **库存事件 → 成本 → 新订单 → 报表**：入库/盘点/红冲必须核对成本基准与事件总量；影响后续开单成本和定价校验。历史订单只有明确逐笔修复才能变更，修复后检查看板、月报、导出和 Agent。
3. **付款记录 → 应计费用 → 利润/实付**：区分新发生费用与支付原应计费用；不能把支付既有费用再次当成新增应计。单品汇总、整单手工记账、自动推荐奖励需有一致的归属和防重规则。
4. **业务写入 → 历史捕获 → 安全撤销**：更新路由表、捕获行/关联列及撤销白名单。新增表仅加入表名不保证已捕获；检查快照前后范围。当前撤销会恢复/删除数据库行，不能把它等同保留资金轨迹的财务红冲；发现后续依赖时须拒绝破坏性回退。
5. **新功能 B 引用旧功能 A**：先确定引用的是 A 的当前状态还是历史快照，再检查 A 的改名、改价、软删除、取消、导入、后台任务和撤销；明确历史记录应保留何值。例如新增佣金付款不能仅累加订单佣金，还要适配已有佣金快照和取消链路。

### 历史操作详情展示（2026-10-23）

- `/api/operations` 的 `detail` 由已保存的 `OperationHistory.Changes` 操作前后快照按字段白名单生成，员工签到/签退补充查询员工姓名；前端灰色说明显示详情，不展示原始表名、JSON 或内部行 ID。没有新增数据库字段，撤销仍使用原快照和一致性比较。
- 订单详情优先显示订单号、客户、应付/定金和商品；库存详情显示商品、仓库数量变化；入库、盘点、财务、员工、离职交接和考勤详情显示对应业务名称、金额、数量或状态。未知/缺少字段时退回“操作人、时间、操作已完成”的说明。
- 展示入口是管理员历史操作页面。员工签到/签退位于认证员工 API；管理员和员工业务写入只有注册在 `operationRoutes` 的路由会生成操作记录。图片导入先生成草稿，确认订单走已登记的 `/api/orders`，确认支出走已登记的 `/api/bookkeeping/entries`；旧 Agent 订单确认也走 `/api/orders`，支出确认走未登记的 `/api/ai/agent/actions/:id/confirm`，不会生成历史详情。AgentNative/调度直接写数据库的行为也不会被补录。导出和报表是只读路径，不受影响。
- 详情生成不会扩大 `operationRoutes`、`buildOperationCapture` 或 `undoableOperationTables` 覆盖范围。R1 曾修正员工即时入库路由配置及商品关系捕获；2026-10-23 员工端即时入库入口和 POST 路由已移除，直接盘点的操作捕获保持生效，旧操作快照不清理。R10 的其他权限与撤销覆盖缺口仍待专项检查。无新增表/列，数据库备份结构不变；真实备份恢复本次未执行。

## 5. 已知断点与需确认的业务意图

R2–R10 是静态代码追踪发现、尚未在真实或测试数据库中复现的未修复断点；优先级是后续处理建议。R1、R11、R13 已修复但未做数据库端到端验证。R12 描述本次员工离职交接实现，业务测试与恢复演练仍待验证。修复其他断点时应先建立可复现的回归场景，再更新本表。

### R1：员工即时入库的历史捕获曾按旧申请配置（历史缺口已修复，入口现已移除）

- 原证据：`CreatePendingInbound` 改为调用 `applyStocktake` 后，实际修改 `products`、`stocktake_records`、`inventory_logs`，可能创建 `historical_cost_repairs`；操作路由仍只捕获 `pending_inbounds`。
- 历史修复：员工即时入库曾注册在 `operationRoutes`，并按商品 ID 捕获盘点记录、库存流水和成本修复；直接盘点使用相同的商品关联范围，不把并发写入的其他商品行带入撤销快照。
- 当前状态：2026-10-23 已移除员工即时入库页面入口、客户端调用和 `POST /api/pending-inbounds` 路由。直接盘点的历史捕获保留；历史入库申请仍可查询/审核，历史操作快照不清理。
- 验证边界：仅静态核对路由、关系捕获和撤销白名单；本次未运行真实操作后撤销的数据库链路。

### R2：历史入库改价与真实退款金额没有完整闭环（高，部分已修复）

- 证据：2026-10-23 起，`normalizeInboundSettlement` 将新请求中的空值、旧 `cash_purchase` 和 `sale_settlement` 统一归为不扣款的 `sale_settlement` 并清空账户；管理员新入库和遗留申请批准均不写财务扣款。撤销仅对数据库中仍明确标记为旧 `cash_purchase` 且有关联账户的历史记录退款。`UpdateInventoryLogPrice` 对历史记录仍改 `InboundRecord.total_cost`，而不保存原实付快照。
- 影响：新入库不会产生资金退款；旧 `cash_purchase` 记录在改价后撤销仍可能按改后的总成本退回，与原实际付款不一致。旧数据不自动迁移或冲销。
- 处理：本次只阻断新入库扣款并避免新记录凭账户指针退款；历史实际付款的逐笔核对/修复仍需单独授权和审计。采购目前没有供应商应付核销流程，不应由成本登记推断已付款。

### R3：订单取消/红冲仅覆盖主要收款，其他资金副作用未联动（高）

- 证据：开单 `createTradeInExpense` 会写换新支出并扣款；`checkAndPayReferralFee` 会从订单关联账户支付奖励（当前已去掉固定公户 ID 3 的回退）。`cancelOrderWithOptions` 处理库存、客户退款和状态，未见对应换新支出、已付奖励或国补结算的逆向/分摊逻辑。
- 影响：取消后有效订单统计减少，但相关支出/累计回款保留，现金、利润和国补余额可能不再能对应解释。
- 待确认：旧件是否已经接收、奖励能否追回、国补是否已回，不能机械退款。需定义“保留、追收、补偿或禁止取消”的规则，并显示未结事项。

### R4：专业记账与普通支出的经营费用口径分裂（高）

- 证据：`postBookkeepingEntry` 写账户和 `FinancialLog`，不写 `Expense`；看板 `OperatingExpense` 只汇总 `Expense`。图片支出和 Agent 支出共用专业记账路径。
- 影响：相同房租经普通支出录入会扣净利润，经专业记账录入却可能只减少现金，不减少看板经营费用。
- 处理：建立统一的费用事实/分类口径，同时区分关联订单直接成本、采购、换新，避免在统一后重复扣利润；对齐页面、Agent 与报表。

### R5：订单费用的单品汇总、手工累加与付款状态相互冲突（中）

- 证据：`postBookkeepingEntry` 给订单配送/安装/提成/奖励字段累加金额；单品配送/安装接口又用明细合计覆盖订单费用。手工“渠道奖励”未同步 `is_referral_fee_paid`，自动发奖仍以此标志判断。
- 影响：手工费用可能被下一次单品更新覆盖；支付已经计提的提成可能再次增加应计；手工渠道付款后满足自动条件可能重复付款。
- 待确认：记账金额是新增费用还是支付既有应计，建立费用明细归属与付款关联，而不是简单把所有付款累加到订单。

### R6：同名销售/毛利/支出指标在月报、排行、导出中不同（中）

- 证据：看板与 Agent 销售额扣 `discount_amount`，`stats_controller.go` 月报按 `total_amount`；月报/员工排行毛利未扣 `trade_in_amount`，看板会扣。月报支出也未排除 `reversal_pair_id`，看板会排除。`ExportOrders` 还单独计算成本和毛利。
- 影响：同一月份、同一订单在多个页面得到不同结果；不能默认页面正确而把 Agent 回答改成另一套口径。
- 处理：明确指标名称和口径后共用计算，对齐取消、软删除、赠品、折扣、换新、冲销及成本缺失处理。成本缺失不能当作已确认的高利润。

### R7：以旧换新叠加国补时前后端计算基数不一致（中）

- 证据：`CheckoutPanel.vue` 非混付先扣换新金额再乘 15%；后端 `CreateOrder` 非混付按商品总额乘 15%。例如总额 1000、换新 100，前端补贴 135/应付 765，后端补贴 150/应付 750。
- 影响：预览、客户确认金额与实际入账可不同；混付、定金组合还需分别验证。
- 处理：先确定业务基数，再统一预览和服务端计算；用户确认及收据应以服务端最终结果为准。

### R8：逐单国补资料状态与累计回款没有核销关联（中，能力边界）

- 证据：`SubsidySettlement` 无订单关联；`CreateSubsidySettlement` 不分摊订单，概览按累计应回减累计回款且负数截为零。
- 影响：不能据累计回款认定某订单已到账；超额登记或订单取消造成的异常可能被零下限隐藏。
- 待确认：是否需要逐单/批次核销、退款与超额警示；若只保留累计管理，界面与 Agent 必须明确范围。

### R9：调拨流水失败未作为事务失败处理（中）

- 证据：`TransferProduct` 调两次 `WriteInventoryLog` 未检查返回错误，之后仍尝试提交。
- 影响：可能出现库存调拨完成但缺一侧或两侧审计流水。
- 处理：双向流水任一失败都回滚，补写入失败场景验证，不以账户无变化为由省略库存审计。

### R10：权限与撤销依赖覆盖仍需专项检查（中）

- 证据：`routers/router.go` 多个账户、工资、支出、国补及备份恢复接口仅挂通用 `AuthRequired`；路由是否另有控制器权限需逐个检查。操作历史只覆盖 `operationRoutes`，而 `RepairHistoricalCost` 还会改 `inbound_records`，其捕获列表未包含该表；Agent 确认接口也未注册在该路由表。
- 影响：不能从前端菜单隐藏推断员工无权限，也不能从新表有迁移推断有撤销。历史修复撤销可能只回退部分成本事实。
- 处理：按员工/管理员角色验证实际 API；把每项写操作的完整副作用加入捕获验证。此处未进行完整越权或并发依赖安全审计。

### R11：账目期间切换后筛选控件保留旧日期（已修复，2026-10-23）

- 证据：父页面切换“累计/本年/本月”时会重新请求流水，但子组件只在有新日期时才覆盖 `date_range`，导致控件继续显示旧月份；之后点击查询又把旧日期传回接口。财务流水列表和导出接口本身支持任意起止日期，没有一个月的硬限制。
- 修复：期间变化时同步子组件日期（无日期则清空），保留用户已选账户、收支、来源和关键词筛选；关键词匹配条件在列表和导出查询中分组，确保与其它筛选条件一起生效。
- 边界：当前页面默认显示本月。跨月查询需选择起止日期或切到累计；接口按日期范围分页，列表每页最多 100 条，导出返回符合相同筛选条件的全部结果。

### R13：员工盘点遇到零成本商品时曾被成本重算回滚（历史缺陷已修复，2026-10-23）

- 证据：此前员工即时入库与直接/批次盘点共用 `applyStocktake`；商品成本为空时，正数 `stocktake` 流水的单价为 0，成本重算原先直接拒绝并使库存、盘点记录和流水一起回滚，员工端只显示通用失败提示。即时入库入口现已移除，直接/批次盘点仍使用此路径。
- 修复：成本重算现在允许零成本的正数库存事件先登记数量；没有已知成本时商品平均成本保持 0，不推算或套用现价。已有正成本基准时，未注明成本的库存调整保留现有平均成本。若之后出现有成本的入库事件但已有库存仍无成本基准，继续拒绝重算，避免把未知库存按零元加权；管理员可通过核价基准或修复具体零成本入库/盘点流水建立成本。
- 业务边界：新订单仍要求 `orderCostSnapshot` 有效成本；员工端盘点不扣资金、不代表已发生采购付款。此代码变更未增加数据库表/列；真实数据库和备份恢复均未验证。

## 7. 备份与恢复专项关联

本节补充迭代约束。以下为当前工作树的静态观察，尚未做真实导出/恢复演练；运行代码仍可能继续变化，实施时需复核。

### 当前实现与关联入口

- 本机开发入口 `./dev.sh start|status|stop|restart` 管理 Go/Air、Vite 与本机 Docker MySQL；macOS 上引擎未启动时，`start` 打开 Docker Desktop 并等待就绪。`stop` 停止 Go/Air 与 Vite，保留 MySQL 容器及数据卷。该控制面不执行数据库备份或恢复，也不改变生产部署的数据生命周期。
- `scripts/build-deploy-router.sh` 是唯一的一键发布入口：在同一脚本中执行前端构建、Go 编译、Docker 镜像构建、tar 导出、软路由旧包备份、上传和 app 容器重建；不依赖其他部署脚本，也不会在 Mac 上启动或测试 app 容器。部署链路检查点为本机不创建 app 容器、tar 含 `manifest.json`、远端容器镜像 ID 与导入镜像一致且状态为 running。镜像 tar 只包含 app 镜像，不是数据库或整套部署备份；软路由上的数据库、运行密钥和配置不由本机镜像构建覆盖。
- 后端 `system_controller.go` 的 `ExportBackup` / `ImportBackup` 调外部数据库客户端导出和导入 SQL，使用临时文件；导出/导入时限目前分别为 2/10 分钟。客户端检测在 `findMySQLCommand`，MariaDB/MySQL 参数分支在 `mysqlClientArgs`。
- Agent 聊天附件新增 `ai_agent_attachments` 表，原文件字节存 `longblob`、提取文本存 `longtext`，由 `config/db.go` 自动迁移；系统重置从该表清理。现有备份执行全库 SQL 导出，没有表白名单，因此会包含附件原文、提取文本及其会话/消息关联；恢复到旧结构后仍需执行应用迁移并核对附件归属与读取。附件不是操作历史中的可撤销业务副作用。
- 员工离职交接新增 `employee_offboardings`、`employee_handover_tasks`、`employee_offboarding_alerts` 三张表，并扩展员工任职状态；三表已加入自动迁移、系统重置及恢复前后计数。全库 SQL 导出包含数据库结构和行。真实导出/恢复及受支持旧备份升级验证尚未执行，不能承诺恢复已验证。
- `Dockerfile` 最终镜像安装 `mariadb-client` 并检查命令存在，数据库服务在 `docker-compose.yml` 使用 MySQL 8.0。安装和命令检测不能替代实际跨客户端/服务端导出恢复验证，基础镜像或包升级也属于影响源。
- 前端入口为 `src/views/SystemSettings.vue`，还要联查 `src/utils/request.js`、后端路由/权限、实际代理与上传限制。下载按 blob 接收时，服务端错误可能也是 blob，必须正确解析，不能保存成看似正常的 SQL。
- `config/db.go` 在启动时迁移结构；在线 SQL 恢复本身不等于再次执行迁移。恢复旧结构后是否需要重启或显式迁移必须写入操作步骤，并验证现有数据不会被启动逻辑意外改写。
- 当前恢复将 SQL 直接送入数据库客户端，未见在此接口内建立恢复前备份或整库回滚机制；`collectRestoreCounts` 的前后计数仅是观察信息，不能证明全部数据及业务关联一致。
- 导出是数据库备份：保存在数据库中的图片、Agent 聊天附件原始字节、提取文本、草稿和任务状态应覆盖；数据库外的环境变量、密钥、外部文件与部署配置不能仅靠 SQL 还原。新增外部存储时必须更新备份边界。本次附件表迁移的隔离库导出/恢复演练尚未执行，不能据此承诺真实恢复已验证。
