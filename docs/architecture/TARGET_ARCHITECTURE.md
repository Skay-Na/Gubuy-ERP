# 目标架构

继续采用 Vue + Gin + GORM + MySQL 模块化单体。页面、Agent、定时处理器调用同一确定性业务服务；服务拥有校验、授权、事务、幂等、事件与审计。Agent 只负责理解、规划、选择白名单工具、解释结果。

```text
工作台/既有页面/Agent -> 认证与权限 -> Tool Registry / HTTP Controller
                                      -> 统一业务服务 -> GORM/MySQL
用户请求 -> 意图理解/追问 -> 受限只读查询或业务草稿 -> 用户确认 -> 现有业务服务
                                            -> 活动/操作历史/审计
```

## 模块契约

1. Business Capability Layer：逐个从现有 Controller 抽取商品、销售、入库、资金服务，保留原 API；输入必须带经认证的操作人和未来租户上下文。
2. Tool Registry：声明名称、JSON 输入/输出、权限、风险、超时、幂等与审计。服务端按当前身份授权，模型输出不授予权限。读工具限制数据集、时间和返回量。
3. Agent Runtime：已有会话分析继续兼容。持久工作采用数据库任务状态、步骤与租约；恢复时重新取数据，不信任旧模型结果。
4. 主动低库存、潜在缺货提醒、库存扫描及补货建议已按经营要求停用；库存查询仍按实际库存事实回答。
5. 用户请求、澄清与确认：写操作必须先展示可核对草稿，再由用户明确确认后复用现有业务服务。
6. Approval：高风险写入必须有独立授权、有效期、一次性执行、数据版本和预算重验。内部草案与正式采购/付款明确分开；支付自动化默认禁用。
7. Events/Audit：业务服务提交事务时写 outbox，后台处理器幂等消费。活动记录保存依据、步骤、工具、状态和错误分类，避免存储密钥与敏感原文。
8. Workspace：预定义指标、信号、目标、任务、审批、活动组件；保留原 ERP 页面。

## 现阶段边界

现有系统是单店库，不能声称已实现跨租户。历史监测/计划表与记录仍随数据库备份保留，但不注册为运行能力，也不在启动时执行。
